fix(staging): a docs-only merge reconciles both services onto the last built tag

The relay stands down one service at a time when main moves, which
normally converges because the next deployable merge deploys every
service. But a DOCS-ONLY merge builds no images: build-platform-images
publishes a docs-noop marker instead of a supply set, the relay's
manifest step set deploy=false and exited, and the split survived until
the next deployable merge. Observed 2026-08-07: staging web on
prod-bc2fef0 against app on prod-1133e9b.

The docs-only arm now RECONCILES instead of skipping. It resolves the
newest supply-set manifest that is a genuine ancestor of the tip
(scanning newest-first, taking the first valid ancestor), validates the
build_tag is an immutable prod tag, and hands that tag to the SAME
watched one-at-a-time dispatch machinery so BOTH services land on it.
There is still exactly one gh workflow run site. Live-state is never
read: blue/green over digest-pinned task defs makes "live" an ALB
weight, so deploying both deletes the unsound read rather than hardening
it, and a redundant deploy is cheap (a fresh task-def revision of the
same images).

Never backwards: a manifest whose commit is not an ancestor of the tip
is skipped; an unreadable ancestry compare fails closed; a malformed
historical tag is a hard error; no path ends green with a service
undeployed. Out-of-band manual deploys remain uncovered, same as the
ordinary path.

Tests: test_staging_relay_reconciles_a_docs_only_build executes the
extracted manifest script against a fake gh, asserts the resolved tag,
then feeds it to the real dispatch script and asserts both services
deploy onto it. Frozen sha256 of the three extracted relay scripts and
the gate floor (3 -> 4) updated in this change.
